# Проверка перед обновлением Render

Публикация в рамках этой работы не выполнялась. Пользователь обновит
свою существующую версию на Render самостоятельно, когда закончит работу.
Базу данных не переносили и не заменяли.

## Запуск

- Из корня репозитория: `npm ci`, затем `npm start`.
- Репозиторный `.npmrc` не сохраняет внутренние адреса npm-зеркала в lockfile:
  версии и integrity остаются зафиксированы, а загрузка использует реестр среды
  установки. Поэтому Render не должен обращаться к внутренним адресам Replit.
- Если корень сервиса в Render уже настроен как `server`, сохраните
  существующую команду `node app.js`; зависимости устанавливаются из
  корневого `package.json` командой `npm ci --prefix ..`.
- На Render не используйте `npm run dev`: эта команда намеренно включает
  в Replit режим `CATALOG_ONLY=1`.
- В полном сервере `CATALOG_ONLY` должен отсутствовать или отличаться от `1`.
- Сохраните имеющиеся настройки PostgreSQL и JWT в защищённой конфигурации
  сервиса: DB_HOST, DB_NAME, DB_USER, DB_PASSWORD, JWT_SECRET.
  Не коммитьте значения и не меняйте JWT_SECRET без необходимости:
  старые сеансы при смене ключа перестанут работать.
- Порт берётся из PORT; сервер слушает `0.0.0.0`.
- IDM_VTON_SPACE_URL и HF_TOKEN необязательны. Без токена доступность
  публичного Space зависит от его общей квоты; токен не гарантирует
  наличие вычислительных ресурсов.
- `HF_TOKEN` задаётся только на backend, значением `hf_…`, без `Bearer`,
  кавычек и пробелов. Не подставляйте его в браузерный токен входа сайта.
  После истечения сессии или смены JWT_SECRET нужен повторный вход в Silver.Vy.
  Ошибки `AUTH_*` относятся к входу, `HF_*` — к провайдеру. Идентификатор
  ошибки в интерфейсе соответствует безопасной записи в runtime-логах backend.

## Если фронтенд и backend — разные сервисы

Общий клиент `server/public/api-client.js` сохраняет исходную связку
`silvervy-frontend.onrender.com` → `silvervy-backend.onrender.com`.
В Replit и при выдаче сайта самим Express используются относительные URL:
запросы не отправляются на старый сервер.

Для другого домена укажите публичный API-адрес через
`window.SILVERVY_API_BASE` до загрузки скриптов страницы либо измените
публичную конфигурацию общего клиента. Адрес не должен содержать паролей,
токенов или query-параметров. Пустая строка явно включает same-origin.
Разрешённый origin в CORS полного сервера должен соответствовать
домену отдельного фронтенда. Нынешнее правило сохраняет исходный домен.

Фронтенд и backend нужно обновить до одной версии: новые страницы используют
`GET /api/status` и новый контракт `POST /api/try-on` с productId, текущими
мерками лаборатории и подтверждённой калибровкой фото (17 нормализованных
точек). Без калибровки размерная генерация отклоняется с 422.
Старый backend этого контракта не поддерживает. Лаборатория расчёта при
недоступности backend остаётся работоспособной.
Новые плечи, длина руки и кисти сохраняются в существующем JSONB профиля;
новой миграции БД не требуется. Старые профили без этих полей допустимы,
но процент перекрытия кисти в таблице без мерок не утверждается.

## Что проверить после обновления

1. Каталог содержит 8 новых моделей одежды и прежнюю обувь; все картинки
   загрузились. Предметное фото — основное, модельное — дополнительное.
2. `/api/status` сообщает `mode: "full"`, а не `catalog-only`.
3. Вход существующим тестовым аккаунтом, профиль и корзина работают.
4. Сравнение XS–XL реагирует на мерки тела, а неподходящий диапазон не
   заменяется принудительной рекомендацией XL.
5. Для верхней одежды: после отдельного согласия запрос фото-превью
   возвращает изображение либо понятную ошибку квоты/очереди.
6. Для брюк фото-генерация недоступна; расчёт мерок работает.
7. При смене размера или мерок старое фото скрывается.

## Подтверждённые ограничения

Программные и браузерные проверки используют контролируемые ответы
провайдера для проверки логики. Дополнительно выполнен отдельный живой
запрос публичного IDM-VTON для XS и XL на синтетическом изображении
каталога: оба вернули изображения с ручной размерной маской.
Это не подтверждает постоянную доступность очереди, доступ с вашим
HF_TOKEN, живую авторизацию с вашей БД или физическую точность посадки.
Авторизацию и настройки Render нужно проверять после обновления.
Для повторной явной проверки API служит `RUN_LIVE_IDM=1 node scripts/verify-idm-live.cjs`;
это расходует бесплатную квоту внешнего Space и не входит в `npm test`.
Составы, изображения и размеры учебной коллекции условные — это явно
отмечено в интерфейсе и в методике.
